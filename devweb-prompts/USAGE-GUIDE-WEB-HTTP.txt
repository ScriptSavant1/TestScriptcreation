================================================================================
  VUGEN WEB HTTP/HTML (C) USER GUIDE
  Postman / Bruno → VuGen Web HTTP/HTML Script Converter
================================================================================

  Protocol:   VuGen Web HTTP/HTML — classic LoadRunner C-based scripts
  Output:     Action.c, vuser_init.c, vuser_end.c, globals.h,
              [ScriptName].usr, default.cfg, default.usp,
              ParameterFile.prm, collection_data.dat,
              ScriptUploadMetadata.xml
              (+ data/*.b64 or data/*.dat for large base64 bodies)
  CLI flag:   --protocol web-http  (REQUIRED)
  Web UI:     Protocol = "Web HTTP/HTML (C)"

  FOR DEVWEB (JAVASCRIPT) OUTPUT: See USAGE-GUIDE-DEVWEB.txt
  COMBINED REFERENCE:             See USAGE-GUIDE.txt

================================================================================
  SECTION 1 — WHAT GETS GENERATED
================================================================================

  Every VuGen Web HTTP/HTML conversion produces 10 required files:

  C SOURCE FILES (for VuGen script editor):
    Action.c         — All requests (web_url, web_custom_request, correlations,
                       transactions, think time, headers)
    vuser_init.c     — One-time init per Vuser (auth token fetch goes here)
    vuser_end.c      — Cleanup / logout per Vuser
    globals.h        — Standard #include block (lrun.h, web_api.h, etc.)

  VUGEN CONFIGURATION FILES (required for VuGen to load and replay):
    [ScriptName].usr         — VuGen metadata INI (protocol, actions, params)
    default.cfg              — Runtime settings INI (think time, HTTP, log)
    default.usp              — Run logic profile INI (MercIniTree format)
    ParameterFile.prm        — Parameter definitions INI (NOT XML!)
    collection_data.dat      — Parameter values CSV (header + data rows)
    ScriptUploadMetadata.xml — LRE upload manifest

  OPTIONAL (generated when large bodies detected, >500 chars):
    data/[RequestName]_body.b64   — Extracted pure base64 body
    data/[RequestName]_body.dat   — JSON body with embedded base64 fields

  STRUCTURE OF Action.c:
    Action()
    {
        web_set_sockets_option("SSL_VERSION", "AUTO");   // ALWAYS first line

        lr_start_transaction("T01_FolderName");

        web_reg_save_param_json("_accessToken",          // BEFORE producer request
            "QueryString=$.access_token", "Ord=1", LAST);

        web_add_header("Content-Type", "application/json");
        web_custom_request("Login",
            "URL={baseUrl}/auth/login", "Method=POST", "Resource=0",
            "RecContentType=application/json", "Referer=", "Mode=HTML",
            "EncType=application/json",
            "Body={\"username\":\"{username}\",\"password\":\"{password}\"}",
            LAST);
        lr_output_message("Login - completed");

        lr_end_transaction("T01_FolderName", LR_AUTO);
        lr_think_time(1);

        return 0;
    }

================================================================================
  SECTION 2 — PREREQUISITES
================================================================================

  YOU NEED:
  1. An AI tool (GitLab Duo, GitHub Copilot, Claude, ChatGPT, or any AI agent)
  2. Your collection file in ONE of these formats:
       - Postman export: Collection v2.1 (.json)
       - Bruno JSON:     collection.json  (items[] array, no schema URL)
       - Bruno YAML:     opencollection.yml  or  single-request.yml
       - Bruno folder:   Drag the entire /collection folder
       - Single .bru:    One Bruno request file
  3. (Optional) A Postman environment file (.json) for variable values
  4. VuGen 26.1 to open, review, and replay the generated script

  IMPORTANT: Always use --protocol web-http flag (or select "Web HTTP/HTML (C)"
  in the web UI). Without this flag, the converter produces DevWeb JavaScript.

  SUPPORTED INPUT FORMATS:
  ┌─────────────────────┬───────────────────────────────────┐
  │ Format              │ How to get it                     │
  ├─────────────────────┼───────────────────────────────────┤
  │ Postman v2.1 JSON   │ Export → Collection v2.1          │
  │ Bruno JSON          │ Export → JSON (from Bruno app)    │
  │ Bruno YAML folder   │ Use the collection folder as-is   │
  │ Single YAML .yml    │ Any Bruno .yml request file       │
  │ Single .bru file    │ Any Bruno .bru request file       │
  └─────────────────────┴───────────────────────────────────┘

================================================================================
  SECTION 6 — LARGE BASE64 BODY HANDLING
================================================================================

  VuGen cannot handle request Body= strings longer than ~4000 characters
  reliably. Bodies > 500 characters (especially base64-encoded content) are
  automatically extracted to files and referenced via BodyFilePath=.

  HOW IT WORKS:

  Case 1 — Entire raw body is base64:
    Generated Action.c uses:
      web_custom_request("RequestName",
          "URL={baseUrl}/upload",
          "Method=POST",
          "EncType=application/octet-stream",
          "BodyFilePath=data/RequestName_body.b64",
          LAST);
    File: data/RequestName_body.b64 (contains the raw base64 string)

  Case 2 — JSON body with embedded base64 field:
    Generated Action.c uses:
      web_custom_request("RequestName",
          "URL={baseUrl}/create",
          "Method=POST",
          "EncType=application/json",
          "BodyFilePath=data/RequestName_body.dat",
          LAST);
    File: data/RequestName_body.dat (contains the complete JSON with
          {varName} LR parameter references preserved — VuGen substitutes
          these at runtime before sending)

  REGISTRATION REQUIREMENTS:
    Both data files MUST be registered in:
    1. [ScriptName].usr under [ExtraFiles]:
         data\RequestName_body.b64=
    2. ScriptUploadMetadata.xml under <GeneralFiles>:
         <FileEntry Name="data/RequestName_body.b64" Filter="4" />

  Without registration, VuGen cannot find the files during replay.

================================================================================
  SECTION 7 — CORRELATION QUICK REFERENCE
================================================================================

  THREE CORRELATION FUNCTIONS — all MUST appear BEFORE the producing request:

  1. JSON FIELD EXTRACTION (most common — for JSON API responses):
     web_reg_save_param_json("_accessToken",
         "QueryString=$.access_token",
         "Ord=1",
         LAST);

  2. BOUNDARY EXTRACTION (for HTML responses or non-JSON):
     web_reg_save_param("_csrfToken",
         "LB=name=\"_token\" value=\"",
         "RB=\"",
         "Ord=1",
         LAST);

  3. REGEX EXTRACTION (for flexible pattern matching):
     web_reg_save_param_regexp("_sessionId",
         "RegExp=sessionId=([a-zA-Z0-9]+)",
         "Ord=1",
         LAST);

  GOLDEN RULE: The web_reg_save_param_* call must be placed IMMEDIATELY BEFORE
  the web_custom_request() that will return the value in its response.

  USAGE: After the producing request, use {_varName} (single braces, _ prefix)
  anywhere in subsequent requests:
    web_add_header("Authorization", "Bearer {_accessToken}");
    "URL={baseUrl}/orders/{_orderId}/items"
    "Body={\"token\":\"{_csrfToken}\"}"

================================================================================
  SECTION 8 — VUGEN-SPECIFIC TROUBLESHOOTING
================================================================================

  ISSUE 1: "Unresolved symbol" error in VuGen replay
  ─────────────────────────────────────────────────────────────────────────────
  SYMPTOM:  vuser_init.c(17): Error -- Unresolved symbol : lr_get_vuser_id
  CAUSE:    lr_get_vuser_id() does not exist in VuGen Web HTTP/HTML
  FIX:      "Replace lr_get_vuser_id() with lr_whoami(). Correct pattern:
               int vusr_id, scid;
               char *vusr_group;
               lr_whoami(&vusr_id, &vusr_group, &scid);
               lr_output_message(\"[init] Vuser %d starting\", vusr_id);"

  ISSUE 2: Double braces {{varName}} appear in generated C code
  ─────────────────────────────────────────────────────────────────────────────
  SYMPTOM:  Action.c contains "URL={{baseUrl}}/api" — VuGen doesn't substitute
  CAUSE:    AI kept Postman {{var}} syntax instead of converting to {var}
  FIX:      "VuGen C uses SINGLE braces. Replace all {{varName}} with {varName}
             in Action.c, vuser_init.c, and vuser_end.c."

  ISSUE 3: Correlation registration placed AFTER the producing request
  ─────────────────────────────────────────────────────────────────────────────
  SYMPTOM:  {_accessToken} is empty in subsequent requests
  CAUSE:    web_reg_save_param_json comes AFTER web_custom_request("Login",...)
  FIX:      "Move web_reg_save_param_json("_accessToken",...) to BEFORE the
             web_custom_request that returns the token. VuGen processes
             registrations BEFORE making the request — they tell VuGen what to
             capture from the upcoming response."

  ISSUE 4: web_set_sockets_option missing from Action.c
  ─────────────────────────────────────────────────────────────────────────────
  SYMPTOM:  HTTPS requests fail with SSL negotiation errors
  CAUSE:    Missing the mandatory first line in Action()
  FIX:      "The FIRST statement inside Action() must ALWAYS be:
               web_set_sockets_option(\"SSL_VERSION\", \"AUTO\");
             Add it before any lr_start_transaction() call."

  ISSUE 5: ParameterFile.prm generated in XML format
  ─────────────────────────────────────────────────────────────────────────────
  SYMPTOM:  ParameterFile.prm contains <?xml version="1.0"?> <ParamList>...
  CAUSE:    AI used old XML format — VuGen 24.1+ requires INI format
  FIX:      "Regenerate ParameterFile.prm in VuGen INI format.
             CORRECT format:
               [parameter:baseUrl]
               GenerateNewVal=\"Once\"
               ColumnName=\"baseUrl\"
               Delimiter=\",\"
               OutOfRangePolicy=\"CyclicParameter\"
               SelectNextRow=\"Sequential\"
               StartRow=\"2\"
               Table=\"collection_data.dat\"
               TableLocation=\"\"
               Type=\"File\"
               auto_allocate_block_size=\"1\"
               value_for_each_vuser=\"1\""

  ISSUE 6: Large base64 body inline in Action.c (>4000 chars)
  ─────────────────────────────────────────────────────────────────────────────
  SYMPTOM:  Body= parameter contains a 10KB+ base64 string
  CAUSE:    AI did not extract to data/ subfolder
  FIX:      "Extract the base64 content to: data/[RequestName]_body.b64
             Replace in Action.c:
               \"BodyFilePath=data/[RequestName]_body.b64\"
             Register in [ScriptName].usr under [ExtraFiles]:
               data\\[RequestName]_body.b64=
             Register in ScriptUploadMetadata.xml:
               <FileEntry Name=\"data/[RequestName]_body.b64\" Filter=\"4\" />"

  ISSUE 7: Transactions not executing — VuGen skips to return 0
  ─────────────────────────────────────────────────────────────────────────────
  SYMPTOM:  Script replays but no transactions execute; Output shows only
            "Action started" then "Action ended"
  CAUSE:    default.usp is missing the complete MercIniTree hierarchy
  FIX:      "Regenerate default.usp. It MUST contain (among other sections):
               MercIniTreeSectionName= in all root sections
               MercIniTreeSons= linking parents to child subsections
               RunLogicActionType= in child sections
               [RunLogicInitRoot:vuser_init], [RunLogicRunRoot:Action],
               [RunLogicEndRoot:vuser_end] child subsections
             Use the exact template from 06-MANDATORY-FILES.txt."

  ISSUE 8: web_add_header not applying to all requests
  ─────────────────────────────────────────────────────────────────────────────
  SYMPTOM:  Authorization header is sent with the first request but missing
            from all subsequent requests
  CAUSE:    web_add_header applies ONLY to the NEXT single request
            (unlike DevWeb's persistent defaults.headers)
  FIX:      "Emit web_add_header(\"Authorization\",\"Bearer {_accessToken}\")
             BEFORE EVERY request that needs the auth header.
             There is NO persistent default header mechanism in VuGen C.
             Wrong:  set header once, then make 5 requests (only 1st gets it)
             Correct: set header immediately before each of the 5 requests."

================================================================================
  QUICK COMMAND REFERENCE
================================================================================

  CLI (code-based converter):
    Basic:
      node src/cli.js convert -i collection.json --protocol web-http -o ./output/

    With environment file:
      node src/cli.js convert -i collection.json --protocol web-http \
        -e environment.json -o ./output/

    Multi-script mode (one script per top-level folder):
      node src/cli.js convert -i collection.json --protocol web-http \
        -m multi -o ./output/

    Bruno YAML folder:
      node src/cli.js convert -i ./collection-folder/ --protocol web-http -o ./output/

  Web UI:
      node src/web/server.js   (open http://localhost:3000)
      Protocol radio: select "Web HTTP/HTML (C)"

  Analyze without generating:
      node src/cli.js analyze -i collection.json

  AFTER GENERATION — OPEN IN VUGEN:
    1. Open VuGen 26.1
    2. File → Open → Script
    3. Navigate to output folder
    4. Select [ScriptName].usr
    5. VuGen loads all .c files and config automatically
    6. Replay to verify
