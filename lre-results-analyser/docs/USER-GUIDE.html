1. What this tool does

After a LoadRunner Enterprise (LRE) test finishes, LRE keeps the raw results: a folder (or ZIP) full of files that record every single thing the virtual users did. The Results page reads those raw files and turns them into:

  • a dashboard in the browser, with these tabs:
    OverviewTransactionsChartsErrorsWorkloadInsightsValidation
  • downloadable reports: Excel, Word, PDF, HTML and JSON.
Your data stays on your computer. The browser reads the files directly from your disk; nothing is uploaded to or stored on the server.

2. Getting started

  1. Open Results in the PerfX menu.
  2. Choose the run's raw-results ZIP (for example RawResults_2144.zip) or its unzipped folder.
  3. Wait for the progress bar (a 1 GB run takes about a minute).
  4. The dashboard opens on the Overview tab.

3. Words you will see

The statistics columns

Imagine a transaction ran 10 times with these times (seconds): 1, 1, 1, 1, 1, 1, 1, 1, 2, 10.

4. The top bar and settings

  • Run name and verdict — the test name and an overall result: No significant issues, Review findings or SLA not met.
  • Export buttons — Excel, Word, PDF and More (HTML, JSON, redacted JSON).
  • Analysis window — by default the detected steady state. Type a start and end (hh:mm:ss from the test start) and press Apply; Detected resets it. Every tab and export follows this window.
  • SLA — choose the percentile (P90 by default) and a default threshold in seconds, then Apply. You can also type an SLA per transaction in the Transactions tab. SLAs are remembered for this test in your browser.
  • Chart granularity — the size of the time slots the charts and the Excel Time Series sheet use. Auto (the default) gives at most 1,500 points over the whole test (for example 30 s for an 8-hour test, 120 s for a 27-hour test). You can choose a coarser size (for example 5 min or 10 min) for smoother charts; the change is instant. It never changes the results table — see section 7.

5. The tabs

Overview

  • Key figures (tiles): duration, peak VUsers, steady-state length, transaction instances, TPS, failed transactions (and %), errors, hits per second.
  • Test: scenario name, project, controller version, start/end time (local and UTC), schedule, scripts.
  • Schedule — planned vs actual: what the test was set up to do next to what really happened. Big differences mean the test did not run as planned.
  • Load generators: which machines ran how many VUsers.
  • Key findings: the most important automatic findings (see Insights).
  • Charts: load and throughput over time; response time per transaction.

Transactions

The main results table, one row per transaction, grouped by script.

  • Steady state / Full run switch: Steady state uses only the analysis window (best for judging performance); Full run includes ramp-up and ramp-down.
  • Columns: Transaction, Count, Pass, Fail, Fail %, Min, Avg, Max, Std dev, P50, P90, P95, P99, TPS; in steady state also SLA (s), Result (PASS/FAIL) and Apdex; plus a small P90 trend line.
  • Sort by clicking a column header; filter by typing part of a name.
  • Click a row for details: distribution of response times, behaviour over time (avg, P90, P95, max), a latency heatmap and the figures per load generator.
Pass and Fail are always whole-run counts, also in the steady-state view.

Above the table a note says how the figures were calculated, for example "Exact: every transaction instance, no granularity (2,817,862 passed instances)". For extremely large tests (more than 20 million transaction instances) it turns orange and says "Histogram…": Count, Min, Avg, Max and Std dev are still exact, and the percentiles are within 0.5 %.

Charts

Pick transactions on the left (5 slowest, 5 busiest, All, None) and the metric (Avg, P50, P90, P95, P99, Max). The shaded band is the analysis window. Drag the slider or scroll to zoom.

The line above the charts shows the granularity in use (e.g. Granularity 120 s (auto)); change it with Chart granularity in the settings bar. Each point is one time slot: its Avg is the average of the transactions in that slot, its Max the slowest one in that slot.

ChartWhat to look for
Load and throughputVUsers and TPS over time. TPS should be flat during steady state.
Response time over timeLines should be flat. A rising line = slowing down; a jump = something changed.
Transactions per secondPer-transaction throughput; dips usually mean slow responses or errors.
Latency heatmapDots per time × response-time band. Two bands = two behaviours (e.g. cache hit/miss); a dark top band = slow tail.
Throughput vs response timeEach dot is a time slot. A curve that bends upward at high TPS marks the capacity limit.
Errors over timeWhen errors happened — compare with response-time spikes.
HTTP responses per secondCount per HTTP status code (200 = OK, 4xx/5xx = problems).
Throughput (bytes received)Data downloaded per second.
Load-generator CPU and memoryShould stay below about 85 %. Above that, the load generator itself may slow results down.

Response time per VUserOne row per VUser. A single bright row = one problem user or data record.

Errors

  • Grouped errors: similar messages are merged (numbers and IDs become <n>), with count, code, script, VUsers affected, load generators, first and last time.
  • Errors over time chart.
  • Error log: every error, searchable by message, code, VUser or load generator.

Workload

  • Scripts: protocol, VUsers, load generators, pacing, think time, iterations planned vs achieved (95 % or more is green).
  • Load generators and hosts: VUsers per machine, CPU and memory peaks.
  • VUsers: every virtual user with its group, script, machine, when it ran, iterations and average response time.

Insights

Automatic checks, each with a short explanation and the numbers behind it.

SeverityMeaning
HighLikely affects the test result — act on it.
MediumWorth investigating.
Low / InfoFor information.
GoodA check that passed.

Checks include: VUsers and steady state as planned; pacing achieved; transactions getting slower over time (trend) or changing level at one moment (step); spikes, and whether errors happened at the same time; a slower load generator; LG CPU and memory; errors and failed transactions; SLA and Apdex; stable throughput; clock-skew samples.

Validation

  • Method: how each figure is calculated.
  • Files used: which raw files were found.
  • Self-checks: OK INFO WARN FAIL. FAIL means the results cannot be trusted (e.g. RawData.eve missing); WARN means something unusual that is explained in the text.

7. Why some numbers differ from the LRE HTML report

Short answer: this tool reports what each transaction really took. LRE's summary table smooths the numbers before it shows Minimum, Maximum, Std. Deviation and 90 Percent. Count, Pass, Fail and Average are not affected by smoothing, so they always match.

What smoothing means. LRE first puts the transactions into small time slots and takes the average of each slot. It then shows the fastest slot average as "Minimum", the slowest slot average as "Maximum", and so on.

Example — three logins in the same slot took 1 s, 1 s and 10 s:

This toolLRE summary table
What is used1, 1, 10the slot average: 4
Max10 (the real worst case) 4
Min14
Average44 — the same

So LRE's Maximum is lower, its Minimum is higher, its Std. Deviation is smaller, and the Average is identical. Transactions that run rarely (one per slot) are not changed by smoothing — that is why some rows match exactly and others do not.

Proof from a real run (2144). LRE's own raw summary file (sum_data/graph_4.dat) records a single 14_03_Search_ClickResultLink that took 41.66 s and one 14_04_Back_to_MyItems that took 2.04 s. This tool shows those values (and the 45.80 s instance next to them). The LRE summary table shows maxima of 7.421 s and 0.363 s.

Is it the "(do not Include Think Time)" filter? No. This tool also removes think time. If it were the cause, the averages would differ too — and they match for every transaction.

Which numbers should I use? Use this tool's numbers to find real slow transactions and to judge SLAs. Use LRE's table only when a figure must be quoted exactly as LRE shows it.

Granularity — what it is and where it is used

Granularity is the length of the time slots used to group transactions (5 s, 2 min, 10 min…).

WhereGranularity?
Results table (Transactions tab, Excel transaction sheets, reports)No — calculated over every single transaction, whatever the size of the test
Charts and the Excel Time Series sheetYes — Auto, or a coarser size you choose
Why can I not choose a granularity for the results table? Because grouping hides the truth: with 5-minute slots, a 45-second transaction that sits in a slot with nine 4-second ones would show as about 8 seconds. That is exactly why LRE's table looks different. Large tests do not need it either — the tool reads the file in a stream and keeps the statistics compactly, so even hundreds of GB are handled without grouping.

8. How to read a report in five minutes

  1. Overview — verdict and tiles. Did the test run as planned (VUsers, steady-state length)?
  2. Insights — High and Medium findings. Read these first.
  3. Transactions (steady state). Sort by P90. Compare with the SLAs. Look at Fail %.
  4. Charts — Response time over time. Flat lines are good; rising lines or spikes need explaining.
  5. Errors. What failed, how often, and when.

10. For the admin team

  • Where it lives: lre-results-analyser/ in the PerfX repository. The page is served at /results-analyser (also under /converter); static files at /ra, /ra/engine, /ra/report.
  • Privacy: processing happens in the user's browser (Web Worker). The server only serves the page; it never receives result files.
  • Command line (large runs, automation):
node lre-results-analyser/cli/analyse.js "D:\Results\RawResults_2144.zip" --xlsx run.xlsx --html run.html

Options: --xlsx, --docx, --html, --out result.json, --sla 3, --sla-pct 95, --window 600-28800 (seconds from start), --granularity 600 (charts / Time Series only), --exact-limit 100000000 (exact percentiles for very large runs; ~12 bytes per instance), --redact, --quiet. Exit code 0 = OK, 1 = a self-check failed, 2 = usage or read error.

  • Very large runs (hundreds of GB): run the CLI on a machine close to the files, with more memory for Node, e.g. node --max-old-space-size=16000 lre-results-analyser/cli/analyse.js … --exact-limit 500000000. Without --exact-limit the tool still works and switches to histogram percentiles above 20 M instances.
  • Diagnostic: --lre-granularity 2 also prints LRE-style smoothed figures to the console, to compare with LRE's HTML table. They are never put into the reports.
  • Tests: npx jest lre-results-analyser (synthetic data only — never commit real results).
  • How it works: README.md (method table) and docs/SPEC-RawData-eve-REVERSE-ENGINEERED.md (byte layout of RawData.eve, validation against LRE on runs 59 and 2144).
  • Validated: names, counts, pass, fail, averages, hits, HTTP codes and throughput match LRE exactly on runs 59 (14 transactions) and 2144 (516 transactions).
