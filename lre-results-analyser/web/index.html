Granularity

What does “Granularity” change?

Exact — every transaction recommended

Every transaction your users made is counted on its own. Max is the slowest real response, and the percentiles (P90, P95…) are of real responses. Use this for SLAs, sign-off and finding slow requests.

5 s … 1 h — LoadRunner-style (averaged)

The run is cut into time slots of the chosen size. Inside each slot, the response times are first averaged — separately for each VUser when “per VUser” is ticked. Min, Max, Std Dev and percentiles are then calculated from those averages. Count, Pass, Fail and Average do not change. The charts use the same slot size.

When should I use it?

When your numbers must match a LoadRunner Analysis report that has Data Aggregation switched on (Analysis → Tools → Options → Result Collection → Data Aggregation → Aggregation Configuration). Choose the same granularity here, and tick “per VUser” if “VuserID” is ticked there.

What to watch out for

Averaging hides slow responses. Example: in one 200-second slot a VUser has ten 1-second responses and one 40-second response. The slot counts as 4.5 s, so the 40-second response no longer shows as the Max. That is why the exact view is the default.

Very large runs

Runs with more than 20 million transactions are summarised while they are read. For those, 200 s is prepared automatically; other sizes need the command line (--granularity 300). Granularity does not make reading faster — reading the file is the slow part.
