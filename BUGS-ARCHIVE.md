### v2.10.13

| ID | Severity | Description |
|----|----------|-------------|
| BUG-040 | High | VuGen JS engine (`lre-utils.js`/`lre-utils.dat`) threw `SyntaxError` at line 1589. Root cause: 21 occurrences of ES6+ trailing-comma syntax (`,` before a closing `)` or `]`) present in both files — 18 in function call argument lists and 3 in array literals. ### v2.10.10

| ID | Severity | Description |
|----|----------|-------------|
| BUG-036 | Critical | DevWeb + VuGen: collections with **multiple distinct JWT-signing pre-request scripts** (each producing a different output variable with different claims — e.g. a primary `jwt_token` used for the Authorization header, plus a secondary JWT used as the raw request body for a registration endpoint, as in `DEPOSITS_TEST_CLIENT_NWB.postman_collection.json`) only generated the PRIMARY JWT. The secondary request's body/var resolved to null/empty. Root cause: the architecture assumed exactly one JWT pattern per script — `detectJwtUsage()` (DevWeb) and the inline JWT scan in `analyze()` (VuGen) blended every detected output var into one `jwtVarNames` array and kept only the claim map with the most fields, discarding the secondary script's distinct claims/output var entirely. Also, `jwtVarNames[0]` was sometimes a library-loading flag name (e.g. `"jsrsasign-js"`) rather than the true primary token var. Fix: new `this.perRequestJwt` Map (`requestName → {claimMap, outputvar}`) in both generators; after the existing primary-JWT scan, a second pass identifies the true primary output var (filtering library names via `_LIBRARY_RE`) and scans each request's OWN pre-request script independently — any JWT detected with a DIFFERENT output var is stored as a per-request JWT, generated fresh inline in that request's codegen (DevWeb: `generateRequestCode()` calls `getJwtToken()` directly, no expiry caching; VuGen: new `generatePerRequestJwtCode()` calls `createJWT()` directly — NOT `refreshJWT()`, since a per-request JWT must never be cached/reused across iterations). VuGen needed a new `_extractPreScript(request)` helper (DevWeb already had `extractScriptFromRequest()`). Per-request JWT output vars are excluded from DevWeb's null-init (`generateGlobalVariablesInit()`) the same way the primary JWT is. |
| BUG-035 | Critical | VuGen Web HTTP/HTML: the primary JWT's value was **never actually substituted** into the request body/headers at runtime. `web_js_run`'s `ResultParam=` always stores the JWT under an underscore-prefixed LR param (`_jwt_token`, matching the `outputParam.startsWith('_') ? outputParam : '_' + outputParam` convention used for `refreshJWT`'s `tokenParam` arg), but `replaceParameters()` only added the `_` prefix for `perRequestVars` (UUID/nonce) — JWT output vars fell through to the plain-name branch (used by correlation targets), emitting `{jwt_token}` instead of `{_jwt_token}`. Since no LR param named `jwt_token` (without underscore) was ever set, `{jwt_token}` resolved to nothing at runtime — silently breaking every VuGen script with a JWT used as a client_assertion or request body. Discovered while implementing BUG-036 (the same mismatch would have broken the new per-request JWT feature). Fix: `replaceParameters()` now also adds the `_` prefix when the variable is a JWT output var (`this.jwtVarNames` or any `perRequestJwt` output var). |

### v2.10.9

| ID | Severity | Description |
|----|----------|-------------|
| BUG-034 | Critical | DevWeb + VuGen: `detectScriptSetVariables()` declared one `/gm` regex (`setPattern`) and reused it across multiple `exec()` loops on different strings. In JavaScript, `/g` regexes maintain `lastIndex` state on the regex object itself — it does not reset when you call `exec()` on a new string. After `scanItem()` exhausted the regex on the collection's event scripts, `lastIndex` was left at a non-zero position. When the requests.forEach() loop ran, `exec()` started from the wrong position and missed matches — especially on short 2-line scripts like `postman.setEnvironmentVariable("access_token", ...)`. This was silently lenient in Node 16 (V8 9.x) but became a hard failure in Node 18+ (V8 10+) which strictly maintains `lastIndex` per the ECMAScript spec. Fix: add `setPattern.lastIndex = 0` before every `while (exec())` loop that starts a new string, in both DevWeb and VuGen generators. |
| BUG-033 | Critical | DevWeb + VuGen: `analyzeRequests()` has a strict producer-before-consumer ordering constraint (`producedAt < i`). In many real-world Postman collections the token endpoint is placed AFTER the API requests that consume its token (e.g. in `DEPOSITS_TEST_CLIENT_NWB.postman_collection.json`, "3. Access token" is at index 6 while all consumers are at indices 0-5). The filter `producedAt < i` never passes for any consumer → 0 correlations → no extractor, no header injection. This has always been the behaviour; it was NOT introduced by any Node.js or regex change. BUG-031 (collection-level auth) was a partial fix — it added collection auth scanning but did not bypass the ordering constraint. Fix: new `injectScriptExtractors()` method in both generators, called after `analyzeRequests()` and `injectJmxExtractors()`. It iterates all requests, extracts post-response test scripts via `correlationDetector.extractTestScript()`, parses variable assignments via `correlationDetector.extractSetVariables()`, and directly injects a correlation for any script-set variable not already covered. Bypasses the ordering constraint entirely — token endpoint can appear anywhere in the collection. Also adds the variable to `scriptSetVarNames` so it's classified Tier 1 dynamic (`load.global.*` / `{varName}`). |

### v2.10.4

| ID | Severity | Description |
|----|----------|-------------|
| BUG-029 | High | `jwt-helper.js` `generateJWT()` threw `DECODER routines::unsupported` on Node 18+ / OpenSSL 3.x when using a PKCS#1 RSA private key (`-----BEGIN RSA PRIVATE KEY-----`). Root cause: passing a raw PEM string to `sign.sign()` with PSS padding no longer works in OpenSSL 3.x — requires a `KeyObject` with explicit `type`. Additional causes: PEM keys corrupted by YAML `>` folded scalars (newlines→spaces), YAML `|` indentation (leading spaces), CSV literal `\\n` sequences, Windows `\r\n` endings. Fix: (1) `normalisePem()` function handles all four corruption modes + HTML entities; (2) `resolveSignKey()` creates a `KeyObject` with explicit `type: 'pkcs1'` or `type: 'pkcs8'`, falls back to raw PEM string for Node <11.6 where `createPrivateKey` does not exist, with intermediate fallback (no explicit type) for Node 12-14 edge cases; (3) diagnostic `try/catch` wrapper emits a 120-char key preview on failure. Tested: 9/9 corruption modes pass on Node 20 / OpenSSL 3.0. |
